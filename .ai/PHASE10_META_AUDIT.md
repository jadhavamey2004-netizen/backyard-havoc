## Source of truth and current persistent data

Existing local persistence is deliberately separate from Phase 10:

| Key | Owner | Current use |
| --- | --- | --- |
| backyard_high_score | GameEngine | Read at engine construction; updated on game over. |
| backyard_best_combo | GameEngine | Read at engine construction; updated on game over. |
| backyard_reduced_motion | src/main.js | Optional user override; browser preference is used when no override exists. Reads/writes are guarded. |
| backyard_muted | SoundEngine | Mute preference; existing read/write paths catch storage exceptions. |

There is no current profile, challenge, unlock, or equipment persistence. Phase 10 will add only backyard_meta_profile; it will leave all four legacy keys and their meaning intact.

The current GameEngine.onGameOverCallback supplies canonical result stats: score, peak combo, distance, survival seconds, high score, and best combo. This callback is invoked only after the engine enters GAME_OVER and saves legacy records. There is no existing RUN_STARTED or RUN_ENDED gameplay event. The meta layer should start its in-memory run guard from the existing title Start / Play Again callbacks and consume the final result callback for run-completion evidence; it must not invent or depend on an undocumented event.

The existing event flow runs audio and VFX presentation first, then calls the single optional onGameplayEvent observer. Main currently does not claim that observer, so Phase 10 can attach a small read-only tracker there without changing audio/VFX ownership. The tracker must ignore unsupported event types and must never call engine mutation methods.

## Safe and unsafe cosmetic hooks

**Safe hooks:**

- Ball appearance is drawn by GameEngine.drawBall() from Canvas gradients, strokes, and seam colors. A skin can select a static palette there.
- The existing ParticleSystem.addTrailPoint() owns ball/projectile trails and caps the list at 60 points. Trail selections can choose an existing point color/recipe; they cannot add another emitter or exceed the cap.
- VfxDirector receives canonical gameplay events and owns impact presentation. An impact style may select palette colors after a real event. It must not change camera trauma/zoom/impulse, hit-stop, profile counts, score, or event timing.
- Reduced-motion state already reaches the engine and particle system; new presentation recipes should retain the classic fallback under reduced motion and add no extra motion or particles.

**Unsafe hooks:** Matter body creation/properties; ball contact, kick, Power Shot, header, projectile, parry, scoring/combo, destruction, Kevin, Havoc, run lifecycle, and collision handlers. No UI action or cosmetic may write to those paths. Cosmetic equipment is only selected from title Garage; it is not switchable mid-run.

A skin/equipment setter should hold only validated static render selections. It must not recreate, scale, or mutate the Matter ball body. Tests should compare ball body gameplay properties and canonical tuning before/after equipping every cosmetic category.

## Migration and storage risks

- The new profile uses an isolated key, explicit schema version 1, a small allow-listed shape, and no replay, telemetry, account, or timestamp history beyond first/last profile update metadata.
- Missing or malformed JSON loads a new default profile. Unsupported schema versions load safe defaults; no v2 migration is claimed. Future migrations belong at one explicit version-dispatch entry point.
- Known cosmetic/challenge IDs are allow-listed. Unknown fields and IDs are ignored. The three CLASSIC items are always owned; invalid, missing, or locked equipped IDs fall back to their category default.
- Storage property access, getItem, JSON parsing, serialization, and setItem can fail. The profile store must keep a safe in-memory profile and never make game construction or a run depend on persistence.
- The existing GameEngine high-score/best-combo reads/writes currently assume the storage object is usable after a typeof check. That is a gap for a security/opaque-origin storage getter or method that throws. A narrowly scoped try/catch around these existing legacy record operations is required to meet the “game still boots/runs” acceptance case; when storage works, their values and keys remain unchanged.
- Existing backyard_muted ownership already catches storage errors. Reduced-motion preference access already catches errors. Neither will be migrated or deleted.
- Saves contain bounded integer progress and static identifiers only. No arbitrary executable data or unbounded event log is persisted.

## Proposed version 1 profile

Storage key: backyard_meta_profile.

The profile has:

- version: 1
- unlocked: unique catalog IDs such as ball:CLASSIC, trail:CLASSIC, and impact:CLASSIC plus achieved rewards
- equipped: one validated category item ID for ball, trail, and impact
- challengeProgress: allow-listed challenge ID to bounded integer progress
- completedChallenges: unique allow-listed challenge IDs
- lifetimeStats: completed runs, total final score, highest observed combo, destroyed props, Perfect Parries, Kevin hits, returned attacks, and Havoc activations
- firstPlayedAt / updatedAt: short ISO timestamps or null before the first successful profile mutation

Defaults are stable, include all three permanent CLASSIC items, equip CLASSIC in all categories, and initialize every stat/progress value to zero (highest combo starts at 1). The store normalizes loaded data, copies values at its API boundary, ignores unknown fields, rejects future/unsupported schema versions to defaults, and has an injectable storage/clock for deterministic tests. Failed writes do not throw or block gameplay. Run reset, game-over, visibility, restart, and main-menu paths do not clear this profile.

## UI integration points and visual direction

The Phase 9 UI is vanilla DOM over the 2D Canvas game and already owns exclusive panels, focus management, inert behavior, Escape handling, reduced-motion settings, results, and restart callbacks. ui_state.js currently permits TITLE, PLAYING, PAUSED, SETTINGS, RESULTS; UiController maps one panel and one focus target per screen. Phase 10 should add exclusive GARAGE and CHALLENGES title-only panels, focus-return buttons, semantic Back buttons, and accessible list rendering through the existing controller. It should not introduce a second overlay/controller or permit Garage while a run is active.

Extend the current backyard arcade visual language: dark grass/wood-like green panels, high-contrast cream type, Bebas Neue display headings, Outfit UI text, lime/yellow primary action, and restrained orange reward accents. PLAY stays primary; Garage/Challenges are secondary. Menu panels may scroll within the existing overlay on short/mobile screens. The game field remains unobscured during play.

Garage item tiles expose category, name, owned/equipped/locked state, and concise challenge requirement in text and accessible names; locked buttons are disabled and cannot equip. Challenges show player-facing name, description, progress, completion, and reward without raw event names. Results append a short optional summary of newly completed challenges/unlocks after the existing run stats; Play Again remains the primary immediate action and the affiliate stays secondary/results-only.
